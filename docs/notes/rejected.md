# rejected — 已否决的决策

> 记录"不做什么"及其理由，防止遗忘后重复讨论。已否决的提案合并于此文件。

## 渲染方式：不用 Canvas

- **日期**：2026-08-08（首次提出）
- **主题**：卡牌 / 桌面渲染用 DOM 而非 Canvas

**否决理由**：DOM 自带语义、可访问性、原生事件、CSS 布局；桌游场景（拖拽、翻面、堆叠）都是低频交互，不需要逐帧渲染。

**重新引入的条件**：出现真正需要逐帧渲染的需求（大量粒子、复杂动画、千级实体）时重新评估。

---

## 统一抽象：不引入 GameObject / 不统一容器

- **日期**：2026-08-08（首次提出；08/13、08/17 重申）
- **主题**：实体 / 容器统一抽象

**否决理由**：
- **GameObject**（08/08）：只有卡牌一种实体时不需要抽象，等引入第二种实体再抽
- **统一 Container**（08/13，08/17 重申）：Pile 与 HandZone 共享面只有"一个 id 数组"；差异面（坐标、叠放、私有可见性、D 键目标、排序、动画）全是各自特有的。统一成带 kind 的容器 = 合并类型再按 kind 拆开判断，中间层是空的

**相关发展（不是本决策的翻案）**：
- 08/17 实体层引入 `ItemState` 判别联合（`kind` 字段 + `faceUp` 收窄为卡牌专属），为骰子 / Token / 板块铺路——这是**实体字段泛化**，与容器统一无关
- 可见性不靠容器抽象：手牌区 = 座位归属（`Seat.playerId`）私有；pile / 自由牌 = 公开

**重新引入的条件**：容器出现第三种真实共享行为（如通用"容器内排序"）时重新评估。

## Tailwind 版本：不退回 v3

- **日期**：2026-08-08（首次提出）
- **主题**：Tailwind v4 → v3

**否决理由**：类名语法一致，v4 热更新更快；退回需重新配置 config，不值得。

**重新引入的条件**：v4 出现无法绕过的兼容问题时。

---

## 页面全 'use client'：不改造为 server page + 抽 client 组件

- **日期**：2026-08-18（首次提出）
- **主题**：保留 page 为服务端组件、所有客户端 API 抽成组件的边界重构

**否决理由**：
- 本项目是浏览器全客户端架构（WS 连接、localStorage session、dnd 全在浏览器），page 改 server 只是把 'use client' 边界下移一层，客户端 JS 体积不变；当前没有 RSC 数据获取、SEO / 静态渲染需求，收益 ≈ 0
- 逐页评估：play / room / [code] / import / games / login 的页面主体就是交互本身，拆容器组件纯加一层间接；唯二合理的下沉点（(main)/layout 的 WS 状态指示器、page.tsx 重定向改 middleware + cookie）收益微小，不值得现在动
- 现状已核对：所有 'use client' 均真实使用 hooks / localStorage / WS，无一处多余；root layout、`(game)/layout.tsx`、`CardBack.tsx` 未标（纯静态 / metadata），边界正确

**重新引入的条件**：出现纯展示页（规则页 / 关于页 / 静态落地页）时，新页面直接做 server page + 局部 client 组件，不回溯改造现有页面；或出现 RSC 数据获取 / SEO 需求时重新评估。
