# rejected — 已否决的决策

## 渲染方式：不用 Canvas

- **日期**：2026-08-08（首次提出）
- **主题**：卡牌 / 桌面渲染用 DOM 而非 Canvas

**否决理由**：DOM 自带语义、可访问性、原生事件、CSS 布局；桌游场景（拖拽、翻面、堆叠）都是低频交互，不需要逐帧渲染。

**重新引入的条件**：出现真正需要逐帧渲染的需求（大量粒子、复杂动画、千级实体）时重新评估。

## 统一抽象：不引入 GameObject / 不统一容器

- **日期**：2026-08-08（首次提出；08/13、08/17 重申）
- **主题**：实体 / 容器统一抽象

**否决理由**：
- **GameObject**（08/08）：只有卡牌一种实体时不需要抽象，等引入第二种实体再抽
- **统一 Container**（08/13，08/17 重申）：Pile 与 HandZone 共享面只有"一个 id 数组"；差异面（坐标、叠放、私有可见性、D 键目标、排序、动画）全是各自特有的。统一成带 kind 的容器 = 合并类型再按 kind 拆开判断，中间层是空的

**相关发展（不是本决策的翻案）**：
- 08/17 实体层引入 `ItemState` 判别联合（`kind` 字段 + `faceUp` 收窄为卡牌专属），为骰子 / Token / 板块铺路——这是**实体字段泛化**，与容器统一无关
- 可见性不靠容器抽象：手牌区 = 座位归属（`Seat.playerId`）私有；pile / 自由牌 = 公开

**重新引入的条件**：容器出现第三种真实共享行为（如通用"容器内排序"）时重新评估。

## Tailwind 版本：不退回 v3

- **日期**：2026-08-08（首次提出）
- **主题**：Tailwind v4 → v3

**否决理由**：类名语法一致，v4 热更新更快；退回需重新配置 config，不值得。

**重新引入的条件**：v4 出现无法绕过的兼容问题时。
