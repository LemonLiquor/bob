# proposed — 已定方向、未落地的决策

> 已达成共识但尚未实现的目标态。实现后条目迁入 implemented.md（保留决策理由）。

## 架构目标态：协议 → 引擎核心 → DOM 运行时

- **日期**：2026-10-02（首次提出）
- **主题**：白纸重审架构方向（起因：z 轴层叠错乱 + 手牌区位置冲突两个结构性问题）。终极目标 = 自定义桌游 + 朋友网页联机玩绝大部分桌游

**决定了什么**：

- **三层架构**：
  1. **游戏包协议**（JSON，第一版窄协议）：组件（prefab/区）+ 初始状态 + 动作开关；规则执行仍靠玩家自觉（沙盒定位），宽协议（可编程规则）等真有需求再加
  2. **引擎核心**：纯 TS，解释协议 + 校验/应用动作 + 输出场景描述（实体/位置/z/图，纯数据非 DOM）。平台无关，浏览器与 Node 双端运行（服务端权威的执行体）
  3. **运行时**：Web 运行时（交互 + DOM 渲染，消费场景描述）；服务端运行时（房间 + 权威执行，复用核心）。依赖方向单向：运行时 → 核心
- **引擎像 Unity 一样内部分层**：心脏（逻辑）不绑渲染，服务端权威要求核心裸跑 Node（多人时"两个玩家同时拖同一张牌"以服务端顺序应用裁决；锁步确定性方案否决）
- **渲染拍平**：废除版图 DOM 嵌套（BoardContainer），所有实体渲染为同一容器平级兄弟，位置 = `worldOf(entity)` + 祖先拖拽 delta（UI 层），zIndex 全局单一维度，被拖实体恒置顶。根治嵌套层叠上下文导致的 z 序错乱。与 implemented"版图跟随"note 的张力：当时的否决语境是换算散落 + 弹回；现在换算集中在渲染入口一处（worldOf 唯一纯函数 + dragDelta 已有状态），实现时该 note 交叉更新
- **位置双语义**：空间语义（版图摆位/弃牌堆）留世界坐标；归属语义（手牌 + 个人布置区）= 挂 Seat 的区容器，**锚定视口按观察者解析**（自己的区在屏幕底部、别人的折叠在边缘）——"下方"对每个玩家都是自己的，斗地主抽象与桌游沙盒兼容。区内实体仍是 EntityState（可翻可叠可拖回世界），parentId 相对坐标机制复用
- **渲染技术选型**：DOM 为主（几百实体 + 视口裁剪可撑绝大部分桌游），引擎核心吐场景描述保持渲染可替换；换 WebGL（PixiJS）触发条件 = 同屏可见实体稳定 >500 且裁剪后仍卡，或真出现逐帧动画需求（rejected.md"不用 Canvas"条款不变，此处为其补充重评触发线）

**后续顺序**：渲染拍平 → 个人区 → 协议层提炼。功能原语（骰子/计数器/锁组/便签）按 TODO 渐进。
