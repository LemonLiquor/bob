# 协作实践

从项目开发中总结的协作方法。核心循环:

```
讨论方向 → 质疑提案 → 达成共识 → 落盘文档 → commit
    ↑                                  ↓
    └────────── 下一个话题 ←───────────┘
```

## 先讨论,再写代码

在写第一行代码之前,先把架构、需求拆分、文档审查讨论完。AI 最擅长生成,但**方向比速度重要**--讨论阶段把泛用性、学习成本、过度设计三条线厘清,后续少返工。每个设计决策都经过"提出 → AI 分析 → 你的判断"三个步骤,不跳过。

## 给 AI 分配角色

输出需求前切换视角:PM(切片对应、依赖)、Tech Lead(过度设计)、Developer(可执行性)、QA(验收可验证)、UX(尺寸/颜色/间距)、DevOps(依赖)。角色约束输出方向,不只是"帮我写代码"。

## 需求三字段格式

- **做什么**:具体技术动作,列出关键字段名、文件路径、函数名。不给模糊空间
- **验收标准**:客观可判断的完成条件。包含具体数值(尺寸、颜色)、文件路径、行为描述
- **关联**:该需求依赖哪些前置需求、被哪些后续需求依赖

这个格式同时约束 AI 输出和你的输入--模糊的需求写不进这个格式。

## 质疑提案

AI 容易套模板、过度完备、堆砌技术债。用“**这个有必要吗**”当筛查工具。已否决的提案记录在 `docs/notes/rejected.md`，防止日后重新讨论（见 `docs/notes/README.md`）。

## 文档即上下文

所有讨论结果落盘为文件。讨论结束 = 文档落盘,不依赖对话记忆。新 session 读 AGENTS.md + 相关文档就能重建上下文,不需要重说一遍。

## 逐步构建,不一次到位

每个阶段只做下一步需要的事。回答"当前最小可做的是什么",而不是"最终完整的应该是什么"。Phase 不需要的库不装,不需要的抽象不写。

## 用真实约束做决策

选型不追求炫技。"互联网公司广泛使用" > "社区评分高"。数据驱动,而非偏好驱动。
